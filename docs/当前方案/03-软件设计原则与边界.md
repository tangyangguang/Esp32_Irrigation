# 03 软件设计

## 设计结论

产品方向固定接入 IoT 平台及平台微信小程序：主固件使用 Esp32Base IOT Profile，本地 Web、灌溉业务核心与 MQTT 平台接入并存于同一个固件，不维护两套固件。本地设备能力（执行链路、计量、调度、记录、本地页面）与平台对接均已在主机构建中收尾，MQTT 适配按 `platform/iot-device` 的 irrigation-controller v1.3.0 契约接入，只对接本地事实和命令，不另建执行或调度模型。当前主固件为 IOT Profile；真机 TLS/MQTT 与小程序联调需另行授权，未完成前不宣称平台已联调通过。

业务只有一套执行链路：自动调度或本地请求 → App 校验及任务准备 → Executor / Controller → 安全关闭 → 结果保存。来源（手动/自动）、目标方式（时长/水量）和用途（正常/基准学习）彼此独立。Base 不承接灌溉策略；页面不负责计时、保护或最终记账。

## 模块职责

| 模块 | 唯一职责 |
| --- | --- |
| IrrigationApp | 编排配置、调度、执行入口、结束结果和维护门禁 |
| WateringExecutor / WateringController | 控制任务交接与唯一阀泵/流量状态机 |
| WateringScheduler / Store | 本地计划匹配、暂停、防重复小状态和下一次计划查询 |
| IrrigationConfigStore / ParameterConfig | 业务 JSON 与 Base 系统参数衔接；任务使用开始时快照 |
| FlowMonitor / UnexpectedFlowMonitor | 运行流量判断、关阀后持续水流判断 |
| WateringRecordCodec / Store | 紧凑业务结果、持久任务标记、本地历史读写与重启收尾 |
| WateringHistory | 从已有事实计算每日水路统计，不持久化重复汇总 |
| IrrigationAuditStore / IrrigationEvents | 必要操作事实、中文解释及当前 Conditions 映射 |
| IrrigationRecords | 登记两个本地 Store、独立可写性和单条待存审计重试，不含同步状态 |
| IrrigationWeb | 本地页面、输入转换、查询呈现；复用 Base 认证、静态资源与分块响应 |
| DeviceAliveCheckpoint | 稀疏存活时间，用于重启后的停机范围估计 |

不增加通用工作流、事件总线、跨芯片 HAL、第二套任务模型或持久日汇总库。FileLog 不在本轮修改范围。

## 工程结构

新工程保持一层清晰业务目录：

```text
firmware/
├── platformio.ini
├── src/
│   ├── main.cpp
│   └── irrigation/
│       ├── IrrigationApp.*
│       ├── IrrigationTypes.h
│       └── 各职责模块的同名 .h/.cpp
└── test/
    └── 按核心行为划分的本机测试
```

`main.cpp` 只提供 Arduino `setup()` / `loop()` 并调用 `IrrigationApp`。文件名与主要类型一致；不建立只有一个文件的层级目录，也不创建含义宽泛的 `common`、`manager`、`helper` 或通用仓储框架。测试按状态机、调度、配置和记录等行为组织，不为每个类机械复制目录。

## 启动顺序与执行上下文

Base、Web、存储和调度留在 Arduino `loopTask`。`WateringExecutor` 在 classic ESP32 core 1 上以优先级 3、4096 B 栈独立推进原控制器，每次最多等待 5 ms 或一个 tick；它只执行控制/GPIO，不调用 Base 服务或持久化。服务任务单调用者通过一槽同步交接取得实际执行结果，完成汇总保留到服务任务确认，状态查询只短时锁定内存。控制任务独立参加 TWDT；不承诺 Flash/cache 停顿期间的硬实时。流量脉冲中断只递增计数器，不做日志、存储、业务判断或硬件切换。

启动顺序固定为：

1. `setup()` 第一项直接初始化 `BoardHardware` 并关闭泵信号、全部阀 PWM 和阀驱动总使能。
2. 在全部执行输出已经安全关闭后初始化 `StatusIndicator`；初始化期间慢闪，任何启动失败转为快闪，但灯光不得改变输出安全状态。
3. 初始化 I2C，并将定稿的 DS3231 总线交给 `Esp32BaseRtc`。
4. 从固件配置读取默认 Web 账号密码并调用 `Esp32BaseWeb::setDefaultAuth()`，注册业务 Web 路由和文件系统格式化后的业务回调。
5. 调用 `Esp32Base::begin()`，由基础库初始化时间、文件系统、Conditions、WiFi 和 Web 等公共能力。
6. 基础库启动成功后立即调用 `Esp32BaseWiFi::setPowerSave(true)`，启用 WiFi modem sleep。
7. 加载业务配置、自动调度小状态及本地历史，并恢复未收尾任务标记。
8. 只有所需配置校验通过后才进入业务就绪状态；否则保持全部输出关闭，只开放诊断和重新生成配置入口并使状态灯快闪。

正常服务循环每轮处理控制结果和自动调度，再调用一次 `Esp32Base::handle()`；阀门时序和流量保护不等待该循环。所有 Web handler 必须快速返回，不在回调中执行校准、等待出水或其它长时间流程。

当前固定使用 WiFi modem sleep 作为稳妥节能策略，不增加用户配置项。该模式保持 STA 关联、Web、NTP、OTA、自动调度、流量脉冲中断和业务循环可用，只允许 WiFi 射频模块在空闲间隙按路由器 DTIM 周期自动休眠；首次 Web 请求可能有短暂额外延迟。当前不进入手动 Light-sleep 或 Deep-sleep，不关闭 WiFi，不降低 CPU 频率，也不改变浇水与保护时序。OTA 期间由 `Esp32Base` 临时关闭 WiFi power save，完成后恢复。

主固件为 IOT Profile（在本地 Web 能力之上启用 MQTT），启用 RTC、RecordStore、Conditions、AppConfig、SDK；业务路由 13 条，配置容量 16，静态资产以当前构建登记为准。保留受控 Core 3 完整 TLS 工具链，不以削弱 TLS 换取尺寸。classic ESP32 使用 4 MiB 布局、双 1728 KiB OTA 和 512 KiB LittleFS；2026-09-16 IOT 链接产物 Flash 1,534,835 B、静态 RAM 103,092 B、OTA 镜像 1,534,896 B（槽余约 229 KiB / 13.3%），尺寸优化由用户后续决定，运行峰值未测量，旧镜像数值不代表本轮结果。

## 核心数据

### 持久配置

- `ValveDriveConfig`：全功率吸合时间、水路切换间隔、PWM 频率、维持占空比。
- `PumpConfig`：是否启用、启动延时、停泵后关阀延时。
- `FlowMeterConfig`：仅保存每升脉冲数 K，使用放大 100 倍的定点整数；专业校准属于独立后续任务。
- `FlowProtectionConfig`：无流量、低/高流量和关阀后水流参数及动作。
- `TimeSafetyConfig`：RTC 时间倒退阈值和存活检查点间隔。
- `RunLimitsConfig`：单水路最长运行时间和单次出水量上限，使用 `Esp32Base` App Config 保存。
- `ZoneConfig`：固定编号、启用状态、名称和基准脉冲速率；基准以 `P/s × 10000` 的整数保存，0 表示未设置，页面使用当前稳态流量系数动态换算为三位小数的 `L/min`。
- `WateringPlan`：固定编号、`configured`、名称、`scheduleEnabled`、每日启动时间和各水路运行时长；`configured` 明确表示计划槽位是否存在，`scheduleEnabled` 只表示是否自动执行。

固定硬件引脚、水路数量、计划数量和 UTC+8 时区是产品常量。单水路最长运行时间改为系统参数，默认 120 分钟、范围 1–720 分钟；单次出水量上限默认 100 L、范围 1–1000 L。

当前灌溉配置 JSON 结构固定为版本 5。文件内容、备份和临时副本都必须完整通过当前结构校验；存在配置文件但没有有效当前副本时保持全部输出关闭，不能用默认值覆盖现场配置。

### 运行数据

- `WateringRequest`：一次请求的来源、目标方式、用途、计划快照和各水路执行步骤。
- `WateringStep`：一个水路、本次最长运行时长和可选目标水量；按时长步骤目标水量为 0，按水量步骤携带目标水量和安全时限。
- `WateringSession`：请求开始时生成的配置与步骤快照、当前水路、计时、脉冲和结果。
- `WateringStatus` / `FlowHistorySnapshot`：控制器只读详情及曲线；其它业务状态通过 `IrrigationApp` 查询。网络和页面不持锁渲染，不写控制器内部对象。
- `AutomaticWateringState`：自动浇水总控模式和可选的恢复时间。
- `DeviceAliveCheckpoint`：最近一次周期确认在线的可信时间；只有长时间没有其它带可信时间的业务记录或事件时才写入。
- `WateringStartResult`：启动入口区分未就绪、忙、上一结果待保存、请求错误和硬件失败；配置入口结合保存结果及 `configurationError()`，参数页结合持久化统计与应用状态。
- `WateringRecord`：一次已经进入执行流程的普通浇水最终业务记录，包括尚未建立水流即失败的尝试。
- `ZoneWateringRecord`：一次会话中单个水路的计划值、实际值和结果。

`WateringSource` 只表示手动浇水（Manual）或自动计划（AutomaticPlan）；`WateringTargetMode` 表示按时长（Duration）、单条按水量（Volume）或时长与水量混排（Mixed）；Volume 与 Mixed 只允许手动普通浇水；`WateringPurpose` 表示普通浇水或水路流量学习。结果使用 `WateringResult`，停止原因使用 `WateringStopReason`。`AutomaticWateringMode` 只使用 `Enabled`、`PausedIndefinitely` 和 `PausedUntil` 三种明确状态，`PausedUntil` 以 `resumeAtEpoch` 保存绝对恢复时刻。这些概念保持分开，避免使用脱离上下文后含义不清的通用 `Operation`、`Result` 或 `Reason` 名称。

## 配置模型与存储

- 水路和浇水计划等嵌套业务对象以 `/app/irrigation/config.json` 为权威；阀驱动、水泵、流量保护、运行限制、时间和存储等标量系统参数以 `Esp32Base` App Config 及其 NVS 为运行权威。JSON 只保存 schema_version、revision、zones、plans，不复制标量参数；启动时读取 NVS 并验证组合后的运行约束。
- 自动浇水总控、调度防重复标记和 `DeviceAliveCheckpoint` 是项目 NVS 小状态，不混入计划定义或业务记录。Web 认证由 `Esp32Base` 管理。
- `Esp32Base` App Config 管理可独立校验的标量系统参数；它不管理 6 条水路和 8 个计划的嵌套数据。业务对象继续使用 `Esp32BaseFs`，两类配置不提供重复保存入口。
- 配置包含结构版本和单调递增的内容修订号。结构版本不匹配时进入配置不可用状态，不做自动转换。
- 加载时同时检查当前文件、临时文件和备份文件，选择能够完整解析并通过结构、业务校验且修订号最高的当前版本副本。
- 三个文件都不存在时生成默认配置；只要其中存在文件但没有有效副本，就不能用默认值覆盖现场内容。
- 配置不可用时所有输出保持关闭，页面显示具体错误；通过现有文件管理恢复当前格式配置后重启。无有效副本时不自动覆盖，格式化需单独明确执行。
- 保存时先构造完整副本，校验所有字段和跨字段关系，再写临时文件、回读校验并原子替换。掉电恢复只处理当前结构的临时文件或备份文件。
- Web 表单携带读取时的配置修订号；修订号已经变化时拒绝旧页面覆盖并提示刷新。保存成功后修订号加一，保存失败时运行配置和修订号都不改变。
- 保存成功后一次性替换内存配置。已经开始的操作继续使用自身快照，修改只影响之后的操作。
- PWM 由控制任务比较目标值和已应用值，只在空闲时调整全部阀通道。普通计划/水路保存不参与硬件参数协调。Base 参数页通过只读应用状态显示已应用、待应用或应用失败；NVS 成功不代表硬件生效，失败不回滚已持久化字段。

每个字段先按 `02-业务规则与安全.md` 的有效范围校验，再校验跨字段关系：水路和计划编号与固定槽位一致，名称是有效 UTF-8，所有开启自动执行的启动项没有全局时间冲突，水路时长为 0 或不超过当前单水路最长运行时间，低流量阈值低于 100% 且高流量阈值高于 100%，开启自动执行的计划至少有一个启动时间和一个当前启用水路的有效时长。系统参数页降低最长运行时间时必须结合当前计划校验后再写 NVS，不能写入会让业务配置失效的组合。

## 硬件安全控制

- 固件进入业务初始化后的第一项硬件动作是将 `DRV_SD` 置为关断、泵信号关闭、6 路阀 PWM 为 0。
- 阀与 GPIO 的对应关系严格使用定稿网表：水路 1 至水路 6 依次为 GPIO 33、32、26、25、14、27。
- `BoardHardware` 是唯一能够写阀、`DRV_SD` 和泵信号的模块，并强制同一时刻最多一个阀打开。
- 多水路切换采用先断后通：先停止泵并关闭上一水路，全部输出关闭达到水路切换间隔后，才打开下一水路并启动泵，避免两个阀的启动电流重叠。
- 阀打开后立即输出 100%；独立计时达到吸合时间后切换为配置的维持占空比，不阻塞泵启动和业务循环。
- PWM 使用固定 8 位分辨率，所有阀通道使用相同频率。空闲时频率变更必须重新配置全部通道并再次确认输出为 0。
- 流量脉冲使用中断累计单调递增计数，业务通过无符号差值取得区间脉冲，不在运行切换时清零中断计数器。
- 任意内部错误、配置失效或保护停机都调用同一个立即安全关闭入口。

## 浇水执行模型

`WateringController` 同一时刻只持有一个 `WateringSession`，其内部状态为：

1. `Idle`：没有活动操作，输出保持关闭。
2. `StartingZone`：打开当前水路阀，按配置输出泵控制信号并执行泵启动延时。
3. `WaitingForFlow`：等待流量建立并执行启动阶段无流量保护。
4. `WateringZone`：计算水路运行时长、流量和水量并执行运行中保护。
5. `StoppingZone`：正常结束时先关闭泵信号，按配置延时后关阀，然后进入下一水路或结束。
6. `SwitchingZone`：多水路运行时保持泵和全部阀关闭，等待水路切换间隔后再启动下一水路。

状态名只用于软件内部，页面显示用户可理解的中文状态。所有计时使用 `millis()` 差值，不使用阻塞延时。

正常状态迁移为 `Idle -> StartingZone -> WaitingForFlow -> WateringZone -> StoppingZone`；多水路操作从 `StoppingZone -> SwitchingZone -> StartingZone` 进入下一水路。用户停止进入安全停机路径；保护、配置失效和内部故障从任意活动状态先立即关闭全部输出，再形成结果、记录和事件，不能为了写 Flash 或生成页面而推迟关阀。

执行规则：

- 请求开始时复制水路顺序、水路时长、泵参数、阀参数和流量保护参数，后续配置修改不改变当前会话。
- 阀全功率吸合与泵启动延时并行，不额外增加水路准备时间。
- 水路运行时长从首次检测到有效流量后开始；没有建立流量时不消耗用户设置的浇水时长。
- 正常完成一个水路时使用停泵后关阀延时；未启用泵时直接关阀。
- 非最后一个水路关阀后进入水路切换间隔，间隔期间不建立下一水路的流量基线，也不把余流脉冲计入下一水路。
- 用户停止时立即关闭泵；启用泵时完成停泵后关阀延时，重力供水时立即关阀。
- 无流量、配置失效和内部故障不等待正常停机延时，立即关闭全部输出。
- 当前水路安全关闭后才能启动下一水路。
- 重启后不恢复会话。普通浇水在输出启动前保存任务标记；重启时若没有已提交的最终结果，补记 Incomplete / RebootInterrupted，实际进度、时长和水量标为未知。已有结果不重复追加，具体恢复规则见“记录、审计与持续条件”。
- 对外启动入口统一校验业务已就绪、当前空闲、水路仍启用、目标方式及步骤有效和本次快照完整；按水量时还检查单水路、目标水量及最长运行时限。自动调度、本地 Web 和对接后的 MQTT 平台入口都不能绕过这些校验；对接完成前 MQTT 入口暂不编译。
- 停止命令停止当前整次会话而不是只跳过当前水路；空闲时收到停止命令返回“没有正在进行的浇水”，不产生停止事件。
- 当前水路的原始脉冲从开阀前计数到实际关阀或安全关闭，覆盖流量建立和停泵后关阀阶段；实际浇水秒数只计算从流量建立到正常浇水结束、用户停止或故障发生的时间。
- 会话结束后形成一次不可变结果摘要，包含请求中的全部水路；尚未运行的后续水路明确标记为 `NotStarted`。正常浇水最终结果收尾前不接受下一次请求，避免结果被覆盖。
- 估算水量使用本次会话开始时复制的脉冲/L 系数和原始脉冲计算并保存为 mL。计算使用 64 位整数完成舍入，溢出时标记结果受限，不写入伪造数值。

## 流量监测

- 所有出水用途共用同一个 `FlowMonitor`，无流量判断只依赖原始脉冲，不依赖校准系数。
- 泵启动延时结束后开始一个完整的流量建立超时；超时仍没有有效脉冲时立即保护停机，不再拆分宽限和确认两个串联计时器。
- 流量已经建立后，任意连续无脉冲时间达到运行中无流量超时都立即保护停机。
- 实时流量使用最近 5 秒脉冲窗口和当前脉冲/L 计算。
- 低流量和高流量只有在目标水路已经学习有效基准脉冲速率时启用；当前窗口和基准直接按原始脉冲速率比较，校准系数只用于页面流量和水量换算。连续异常按窗口实际时长累计，任一正常窗口清零；异常确认后更新本次运行报警标记，连续正常达到恢复确认时间后重新布防；最终浇水记录保留报警事实，不另建低/高流量历史事件。配置动作决定只报警还是停止整次浇水。
- 全部输出关闭后按配置等待关阀后检测延时（默认 30 秒），再按窗口检测关阀后水流；完成第一个有效窗口前状态未知，报警持续期间不重复写事件，恢复一个完整窗口后解除并记录恢复事件。一次业务循环内完成关阀、复位监测器和观察状态时必须复用同一个 `millis()` 快照，避免无符号时间差回绕而提前开始检测。
- 水路切换、正常停止和故障停止都要重新建立相应监测窗口，不能沿用上一阶段计时。

## 自动调度

- 调度只使用 `Esp32BaseTime` 提供的可信 RTC/NTP 时间，不直接读写 RTC。
- 启动时间按本地固定 UTC+8 的 `0..1439` 分钟保存；暂停恢复时间按 UTC epoch 保存。运行时统一从同一个时间快照计算本地日期和分钟，不能混用本地 epoch 与 UTC epoch。
- 应用层要求本地日期不早于 2026-01-01。RTC 状态异常或早于该日期且没有 NTP 时间时，自动调度不可用。
- RTC 来源的当前时间比本次启动内已经观察到的最大可信时间，或上次可信浇水记录、事件、检查点时间倒退超过配置阈值时，进入“RTC 时间倒退”状态；默认阈值 5 分钟。NTP 成功校时后接受 NTP 时间并解除该状态。
- 每次检查计划前先判断 `AutomaticWateringState`。`PausedIndefinitely` 不自动恢复；`PausedUntil` 只有在时间可信且达到 `resumeAtEpoch` 后才切换为 `Enabled`。
- 定时暂停只在当前时间可信且没有 RTC 倒退时保存最终的 `resumeAtEpoch`，不保存页面倒计时副本。暂停、手动恢复和到期自动恢复各最多写一次 NVS 并记录一次事件。
- 暂停期间遇到的到点项仍先写入当天已处理标记，然后跳过，不提交浇水请求且不逐项写跳过事件。恢复后不扫描暂停期间的计划。
- 启动或时间刚变为可信时，以当前分钟初始化检查点，不触发当前分钟的计划。
- 正常运行只检查新进入的分钟，不扫描或补执行跳过的时间范围。
- 到点后先持久化“已处理”标记，再提交请求；标记写入失败时禁止启动本次自动浇水，避免重启后重复执行。设备忙或请求失败时仍视为本次已处理，并按启动结果及当前任务类型记录用户可理解的具体跳过原因。
- 每个计划的 4 个启动时间使用固定槽位；一个本地日期的已处理状态用 `(计划编号, 启动槽位)` 对应的 32 位掩码表示，不把可修改的具体分钟作为身份。
- 调度只保存当前本地日期和前一日期的处理掩码。超过 RTC 倒退阈值的回拨已经由时间安全状态阻止自动调度，两天数据足以处理阈值内的同日和跨午夜回拨。该状态连同版本和校验信息保持在基础库 256 字节 blob 限制内。
- 当前分钟只有在本地分钟按正常连续顺序进入时才参与匹配；启动、时间首次可信或分钟发生不连续跳变时，仅以目标分钟重新建立检查点，不运行恰好落入该分钟的计划。
- 修改计划、开启自动执行或恢复自动浇水时，以当前分钟重新建立检查点，不因为配置恰好包含当前分钟而立即启动。
- 下一次计划时间由调度层的只读 `NextAutomaticWatering` 查询模型根据当前有效配置、UTC+8 时间和暂停状态实时计算，不保存为配置。正常状态从当前分钟之后查找；定时暂停从恢复分钟之后查找，恢复所在分钟不触发；每日计划最多向后检查一个完整周期。
- 计划自身的 `scheduleEnabled` 与自动浇水总控相互独立：只有总控为 `Enabled` 且计划开启自动执行时才可由调度启动；手动浇水从计划填入时长时不检查这两个条件，提交仍按手动请求执行。

## 计量参数与水路流量学习

- 灌溉仅保存每升脉冲数 K，使用 P/K 换算水量；专业采样与分析在外部后续任务实现。
- 水路流量学习同样提交单水路操作，从开阀开始执行 10 分钟硬上限。流量建立后每 5 秒生成一个原始脉冲速率窗口，页面保留最近 10 个、判定只使用最近 5 个；所有判定窗口非零，且最大最小差不超过 10% 或一个脉冲量化误差时确认稳定。建议值使用五个窗口的总脉冲和总时间计算，保存为 `baselinePulseRateX10000`。手工输入也换算到同一字段并要求三位小数 `L/min` 精确回算，不保存显示专用副本。
- 学习不写普通浇水记录；只有用户确认并成功保存最终结果时才写信息事件，未得到有效结果或用户放弃时只在当前页面提示。

## 记录、审计与持续条件

watering v8 payload 为 210 B，Base 元数据/CRC 槽额外 24 B，包含任务 ID、可信开始 epoch、来源/目标方式、结果/原因及六路明细（每路含开始相对偏移）。irrigation-audit v4 payload 为 20 B，槽额外 24 B。删除 SDK 信封、平台 ACK 保护和重复自动运行审计。

两个 Store 分别使用 RotateOldest，预算仍为 160/48 KiB。历史总预算 208 KiB，FileLog 128 KiB 保持不变，FS 安全预留及配置/元数据空间维持原预算。段尺寸和保留条数由 Base 按槽大小、字节预算推导，展示 StoreStatus，不能承诺固定条数或无限历史。当前目标的构建容量及验证证据见固件 README；静态资源已有测量，运行堆/栈峰值及物理满容量实验未验证。

任务开始标记位于设备 NVS irrigation/task，234 B（头 4 + Store 世代 16 + payload 210 + CRC 4），低于 Base blob 256 B 上限。写成功后才允许正常任务启动。结束结果冻结原始时间后写入，成功后才清标记。重启不续浇；用最新已提交 payload 的 taskId 判断是否已记账，避免撕裂槽产生 ID 空洞时重复记录。无最终证据时保存不完整结果，进度未知。NVS 读取失败与不存在通过 Base readBlob 明确区分。

Conditions 仅在 RAM 保存观察和确认状态，不要求 NVS 写入。当前状态与历史用途分离，时间倒退与主动暂停分别影响调度；不持久化可重新观察的诊断位。Base appendRecorded 接收已冻结完成时间，复用原 CRC、分段写入和故障机制；真实写入结果不确定时不盲目追加。

配置格式不变。新历史格式不读取或迁移旧试运行数据；旧版本文件不会被自动转换或全盘清理，仍占空间。升级时若需回收，只能针对旧 watering.v7 和 irrigation-audit.v3 测试历史做明确维护，不能连带清除配置、凭据、FileLog 或未知文件。本轮实验核心板烧录未执行上述清理或初始化。

## Web 设计

顶层导航为首页、计划、记录、设置；手动浇水为首页弹层，水路管理直接位于设置页，基准流量学习为下级入口，计划编辑、水路编辑和记录详情沿用原有弹窗，具体信息结构见业务规则。统计集中在 WateringHistory；展示不重新计算保护或决定任务终态。日期按 UTC+8，各水路按开始日期归属；缺失时间、历史淘汰、读取失败和中断未知均明确显示。

页面继续采用 Base 服务端渲染，不引入 SPA。静态 CSS/JS 从 web-src 生成 gzip 只读数组，由浏览器解压，动态 HTML 使用原分块响应；不写 LittleFS、不设运行时解压大缓冲。构建前检查源和生成物一致。修改成功后重定向；表单失败保留输入，防重复提交、编辑离开提示和参数校验分别位于适合的层。

空闲首页轮询运行状态，并在历史变化或定时刷新时重新取每日事实；运行/学习页约每秒取状态，趋势只使用真实采样。页面隐藏停止轮询，失败退避并提示当前值可能过时。计划和设置编辑页不被自动刷新打断。统一简洁样式，禁止左侧彩色竖条与装饰渐变：颜色只使用 `--eb-*` 变量、不写十六进制色值，普通容器圆角统一 8px（胶囊标签保留全圆角），字重只用 400/600/700，页面 CSS 一律作为 web-src 静态资产生成，不在处理器中内嵌 <style>。

## 维护操作责任

- 设备通过 Base guard 拒绝浇水或学习活动中的 OTA/格式化；存在待保存的学习结果时也拒绝。OTA 另需没有待处理结束事实或审计事实。
- 用户负责先查看运行状态，只在没有浇水或流量学习时执行维护操作。
- 重启先关闭全部输出，再结束当前业务并处理必要事实。启动后不恢复任务。
- 格式化 LittleFS 会删除业务配置、浇水记录和基础库文件；系统不自动格式化，也不扫描整个分区判断是否首次使用。新设备首次烧录后若文件系统无法挂载，首页明确说明可能需要初始化；用户确认没有需要保留的数据后，仍通过 System 页主动格式化。已经使用过的设备挂载失败时不得仅凭该提示直接格式化，应先保留可能仍可恢复的数据。格式化成功后按首次启动流程自动创建默认配置和当前版本存储。
- System 页格式化成功后，基础库自动 reload 已登记的原 Store 对象；业务回调不再次 `begin()` 或 `reload()`。回调对已登记 Store 复用 Base 重载结果；启动尚未初始化过的 Store 才首次 begin。回调清理任务标记并依据原对象的新状态同步存储故障标记，并清除项目 NVS 中的自动浇水状态和调度标记，重新加载 `DeviceAliveCheckpoint`，同时丢弃业务派生状态并重新进入首次启动流程。这些状态引用已经删除的配置和记录，继续保留会产生错误关联；WiFi 和 Web Auth 由基础库管理，不属于这组业务状态。格式化开始前必须通过上述业务安全门禁；失败不清理原业务状态。

## 失败处理原则

- 启动时配置不可用：所有浇水命令和自动调度不可用，输出保持关闭。Web 必须区分文件系统不可用、已有配置无有效副本、配置写入失败和其它启动检查失败；只有文件系统不可用时说明新设备首次烧录后可能需要初始化，所有情况都保留人工判断，不自动格式化。
- 计划/水路 JSON 保存失败：继续使用保存前配置，不形成半更新状态。系统参数按 Base 逐 key 写入并显示 partial；应用重新加载实际已保存值，失败时保持安全并显示应用失败，不宣称跨 key 事务。
- 调度防重复状态无法读取或写入：停止自动调度，手动浇水仍可使用。
- 自动浇水暂停或恢复状态写入失败：命令失败并保持原状态；到期自动恢复写入失败时继续暂停。
- 存活检查点写入失败：只失去相应掉电估算精度并提示存储警告，不影响手动浇水或自动调度。
- 两个 Store 独立初始化、登记、恢复和报告故障；即使其中一个加载失败，也登记其定义以保留受管路径、预算和明确格式化恢复。手动浇水要求 watering 可写，自动计划额外要求调度防重复可用；学习不新增 watering 历史。审计故障不能单独阻断健康的手动浇水。
- 已完成浇水结果保存失败时保持待保存汇总并阻止后续出水，输出已经关闭。不得丢弃或覆盖未提交结果，不把写入不确定盲目当作可重试成功。
- 所有错误同时保留稳定代码和中文说明；页面文案不能把“控制信号已输出”描述成外部泵已经真实运行。
